Written for: a tester or QA student working through the upload feature, with each idea tied to Functionality, Data Integrity or Security.

## Functionality

**File formats**
- Upload a valid PDF, DOCX and TXT. Each should succeed and open correctly afterwards.
- Upload unsupported types (EXE, JPG, ZIP, DOC, RTF, XLSX). Each should be rejected with a clear message.
- Change the extension without changing the content (an EXE renamed to .pdf, a PDF renamed to .txt). Check whether the content type is validated, not only the extension.
- Try uppercase or mixed-case extensions (.PDF, .DocX), a double extension (report.pdf.exe), no extension, and a trailing dot or space.
- Try an empty (0 byte) file of each type.
- Upload a TXT in different encodings (UTF-8, UTF-16, ANSI). Check that Thai, Chinese and emoji content survive.

**File size**
- Test the boundary: 19.99MB, exactly 20MB, 20MB + 1 byte, and 100MB+.
- Clarify whether 20MB means 20,000,000 or 20,971,520 bytes. The two readings put the boundary in different places.
- Check that the size limit is enforced both client-side and server-side.

**Progress updates**
- Check that progress moves from 0% to 100% and never goes backwards.
- Check that progress behaves sensibly on a very small file and on a file near 20MB.
- Throttle the network. Progress should still be accurate and the UI should not freeze.
- Cancel mid-upload. Progress should stop and no partial file should remain.
- Upload several files at once. Each should have its own progress indicator.
- Check that 100% is shown only after the server has actually saved the file, not when the last byte leaves the browser.

**Access and workflow**
- Upload files with special characters, very long names, or spaces in the filename.
- Upload two files with the same name. Check whether one overwrites the other or both are versioned.
- Upload the same file twice (duplicate handling).
- Refresh or close the browser mid-upload.
- Lose the connection mid-upload (Wi-Fi off) and see whether it fails clearly or can resume.
- Let the session expire during a long upload.

## Data Integrity

- Upload a file, download it, and compare checksums (SHA-256). They must match byte for byte.
- Check that the file's metadata (name, size, type, upload time, owner) is stored correctly.
- Interrupt an upload partway. No truncated or corrupt file should be saved, and no orphaned record should be left in the database or storage.
- Check for consistency between storage and database. Both a file with no record and a record with no file are defects.
- Upload many files at the same time with several users. Check for race conditions, overwrites and mixed-up content.
- Upload a password-protected PDF, a corrupted PDF, and a DOCX with macros or embedded objects. Check how each is handled.
- Check that very large page counts or complex documents are stored without loss or modification.
- Check whether the system alters the file (compression, re-encoding, metadata stripping) and whether that is acceptable for legal documents.
- Check that timestamps are correct and consistent across time zones.
- Simulate a storage failure (disk full, storage service down) and check for rollback with no partial data.
- Check that a failed upload's retry does not create duplicates.

## Security

**Malicious files**
- Upload a file containing malware (use the EICAR test file). It should be detected and blocked.
- Upload a PDF with embedded JavaScript, a DOCX with malicious macros, and a TXT containing script tags.
- Upload a zip bomb or decompression bomb disguised as DOCX, since DOCX is a ZIP container.
- Upload an XXE payload inside DOCX XML.
- Upload a polyglot file (valid as two formats at once).

**Filename and path attacks**
- Use path traversal in the filename: `../../etc/passwd`, `..\..\windows\system32`.
- Use a null byte in the filename (`file.pdf%00.exe`).
- Use XSS in the filename (`<script>alert(1)</script>.pdf`) and check that it is encoded wherever displayed.
- Use SQL injection in the filename or metadata (`'; DROP TABLE documents;--`).

**Access control**
- After upload, log in as another user and try to view the document. It should be inaccessible.
- Guess or increment document IDs or URLs (IDOR) as another user.
- Try accessing the document URL directly without logging in.
- Check that an admin, or another paralegal in the same firm, cannot see the document unless that is by design.
- Check that search results, thumbnails, previews and caches do not leak the document to other users.
- Check that the document is not publicly reachable on the storage layer (for example an open S3 bucket).
- Replay the upload request using another user's token. Tamper with the owner field in the request.
- Check for CSRF on the upload endpoint.

**Transport and storage**
- Confirm uploads happen only over HTTPS and that HTTP is rejected or redirected.
- Check that files are encrypted at rest.
- Check that storage paths and URLs are not predictable, and that signed URLs expire.
- Check that upload endpoints are rate-limited (brute force, denial of service by repeated 20MB uploads).
- Check that error messages do not reveal server paths, stack traces or internal details.

**Authentication**
- Try uploading when logged out, with an expired session, and with an invalid token.

## Auditing

- A successful upload produces an audit entry with user, filename, size, timestamp and status.
- A failed upload (rejected type, oversized file, network failure, virus detected) also produces an entry with a reason.
- A cancelled upload produces an entry or has a clearly defined behaviour.
- Audit logs cannot be edited or deleted by regular users.
- Audit timestamps and user identity are accurate.
- Check that audit entries do not contain sensitive document content.
- If the audit service is down, check whether the upload fails safely or succeeds without a record. Either way, the behaviour should be intentional.
- Check that audit entries for several simultaneous uploads are not missing or merged.

## Risks to raise with the team
- The acceptance criteria say nothing about virus scanning, encryption, or retention.
- The word "share" in the user story is not covered by any criterion.
- Behaviour on failure and retry, duplicate files, and cancellation is not defined.
